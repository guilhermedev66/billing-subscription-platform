# Product Scope & Milestone Roadmap — Billing & Subscription Platform

See `docs/research/M0-Billing-Platform-Research-Brief.md` for the full domain research and UX reference this roadmap is built from, and `docs/ARCHITECTURE.md` for the technical decisions.

## MVP definition

In scope for MVP (M1–M5): organizations, customers, product/price catalog (flat, per-seat, tiered, metered), subscription lifecycle with proration, invoicing, a deterministic simulated payment gateway with dunning, webhook delivery with HMAC signing and an event log, and the virtual-clock "time travel" simulation console that makes all of the above demoable without waiting on real calendar time.

Out of scope / cut per scope control: real payment processing, multi-currency FX conversion, tax-jurisdiction engines beyond a flat simulated rate, a real customer-facing storefront/checkout, multi-region deployment, microservices.

M6 (dashboard analytics + hardening) is a stretch milestone — build it only once M1–M5 are solid; don't let it crowd out core billing correctness.

## Milestones

Each milestone follows: plan → delegate → implement → test → review (Codex QA / Antigravity) → fix BLOCKER/IMPORTANT → commit → push → next milestone. No stopping to ask after each one.

### M1 — Foundations — COMPLETE
- **Backend:** solution scaffold (per-module Domain/Application/Infrastructure/Api projects), `Directory.Build.props`, `ArchitectureTests` project wired in from day one, Identity + Organizations modules (auth, tenant boundary), `IVirtualClock` service, Serilog + OpenTelemetry wiring, health checks, Docker Compose (Postgres), base EF Core migrations.
- **Frontend:** Vite+React+TS scaffold, Tailwind v4 tokens (zinc/slate neutral, semantic status colors per the research brief §6.2), light/dark theme system, app shell (sidebar, top nav, persistent Simulation Bar placeholder), auth screens, API client (fetch wrapper + ProblemDetails parsing).
- **Exit criteria:** empty-but-running app, authenticated, deployed locally via Docker Compose, architecture tests green, CI pipeline running lint/build/test on push.

### M2 — Customers & Catalog — COMPLETE
- **Backend:** Customers module (CRUD, credit balance, delinquency flag), Catalog module (Products, Prices — all four pricing models), tenant-isolation tests.
- **Frontend:** Customers list/detail (slide-over sheet), Products/Prices pages with the tiered/per-seat price builder.
- **Hardening from QA (Antigravity + Codex QA independent passes):** balance/delinquency are immutable via the public API after creation; cross-tenant customer lookups return a uniform 404 (no existence oracle); tiered prices must be contiguous (gaps rejected, not just overlaps); customer email is unique per organization (DB constraint + 409); `MeteredAggregation` validated against defined enum values; backend email validation tightened to match the frontend; frontend surfaces unmapped server validation errors in a form-level alert instead of dropping them; table rows use real interactive elements for full keyboard support.
- **Deferred, consciously (OPTIONAL, not this milestone):** optimistic concurrency on Customer/Product/Price updates — no financial mutation happens until M3/M4, revisit then; real-time organization-membership revocation (currently token-lifetime bound); a hard ceiling on price-builder decimal input to avoid float/safe-integer edge cases before real money math starts consuming it.

### M3 — Subscriptions — COMPLETE
- **Backend:** Subscription state machine (trialing/active/past_due/unpaid/canceled/paused), proration engine (integer-cents, BigInteger-safe), seat adjustments, optimistic concurrency (real EF concurrency token, proven by a 5-way concurrent HTTP race test). `PastDue`/`Unpaid`/`Recover` transitions are modeled but not yet reachable via any endpoint — reserved for M4's dunning engine. `preview-proration`/`apply-change` compute and return proration but don't yet persist an invoice line item (no Billing module until M4); that seam is commented in the code for M4 to pick up.
- **Frontend:** Subscriptions list/detail, upgrade/downgrade flow with the "Preview Proration" modal (research brief §3, Reference Point 3). Cancellation is immediate-only this milestone (no `cancel_at_period_end` — needs M4/M5 renewal-cron infrastructure).
- **Hardening from QA (Antigravity + Codex QA independent passes):** every subscription mutation (create/apply-change/cancel/pause/resume) requires an `Idempotency-Key`, persisted with a DB-unique constraint and atomic replay — same key + same body replays the stored response, same key + different body is 409; this is the project's first real implementation of the idempotency pattern, meant to be reused by M4/M5's webhooks and payments. Trialing subscriptions are never charged when changing plan/seats (proration zeroes out, price/seat still change) until `trial_end`. Pause is only valid from `Active`; Resume only from `Paused`; plan/seat changes are rejected while `Paused` (must Resume first). Downgrading from a seat-based price (PerSeat/Tiered) to a non-seat price (Flat/Metered) now correctly clears `SeatCount` instead of getting stuck rejecting the request.
- **Deferred, consciously (OPTIONAL, not this milestone):** the proration *preview* for a no-op plan change (same price/seat resubmitted) shows offsetting non-zero credit/charge lines that net to zero — cosmetic only, `apply-change` already correctly no-ops without a version bump; whether an organization/customer may hold prices in more than one currency is an open policy question, cross-cutting beyond Subscriptions, to resolve alongside M4's invoicing design.

### M4 — Invoicing & Payments — COMPLETE
- **Backend:** Billing module (Invoice draft→open→paid/void/uncollectible, proration/credit-note line items, per-org sequential invoice numbering via an atomic Postgres UPSERT) and Payments module (deterministic test-card simulator, dunning retry state machine driven by `IVirtualClock`, day-3/7/14-then-uncollectible schedule). `SubscriptionChangeBillingOrchestrator` turns a paid plan/seat change into an invoice + payment attempt in the same flow that produced the M3 proration receipt.
- **Frontend:** Invoices list + `InvoiceDetailPage` (split-pane paper-style bill left, dunning status/actions right), `PaymentsPage` as a dunning cockpit (at-risk invoices by next-retry urgency, retry-now test-card modal, durable per-invoice attempt history via the M4 attempts endpoint), void action with confirmation.
- **Hardening from QA (Codex QA independent pass, two rounds + a fallback-verified sign-off):**
  - **Cross-module transaction atomicity (BLOCKER-class):** Billing/Payments/Subscriptions are separate `DbContext`s on one physical Postgres database; a payment attempt or a subscription-change-triggered invoice+payment now runs inside one shared connection+transaction (`FinancialTransactionCoordinator`: `Database.SetDbConnection` + `Database.UseTransactionAsync` across all three contexts), so a mid-flight failure rolls back every module's write instead of leaving invoice/payment/subscription state inconsistent. Proven by failure-injection integration tests that swap in a throwing fake service via DI and assert on raw DB state.
  - **Idempotency hash must cover every field that affects the outcome, not just the "primary" ones:** the subscription apply-change idempotency hash was missing `cardNumber` (added when M4 wired billing into M3's endpoint), so the same key with a different card silently succeeded instead of 409ing. Fixed and covered by a same-key/different-card test — this is a general lesson for any future endpoint whose request shape grows after its idempotency hash was first written.
  - **A negative-proration (downgrade credit) invoice has nothing to collect, so it must settle immediately, not sit `Open` forever** — `SubscriptionChangeBillingOrchestrator` now calls `MarkPaidAsync` inline, inside the same atomic transaction, whenever `AmountDueImmediatelyCents < 0`.
  - **Dunning-sweep scope matches the M0 research brief's card table exactly, not by accident:** only `Declined`/`InsufficientFunds` enter the day-3/7/14 retry sequence; `Expired` gets an immediate failure notification with no auto-retry (manual re-attempt with a different card still works); `Requires3DS` (`4000...3022`) records the attempt without marking paid or scheduling dunning — a second attempt with the same card completes the simulated challenge; `ProcessingError` (`...0007`) returns a transient 500 with no persisted attempt.
  - Cross-tenant access (list/get/void/attempt-history/charge/dunning-sweep) returns uniform 404; a concurrency probe confirmed the per-org invoice-number sequence has no race under concurrent distinct-key inserts.
  - Frontend accessibility pass (Antigravity, independent of Codex QA): live regions on payment/3DS-challenge results, per-row `aria-label`s instead of repeated generic button/link text, one borderline color-contrast fix, a screen-reader-audible dunning state on the invoice status badge.

### M5 — Webhooks & Simulation Console — COMPLETE
- **Backend:** Webhooks module (Outbox-based delivery with DB-level dispatch leases, HMAC-SHA256 signing against `IVirtualClock.Now`, delivery log, Inbox-based idempotent inbound event ingestion with a per-org projection). Full virtual-clock time-travel API (`+1`/`+7`/`+30` days, advance-to-next-anchor, trigger renewal cron, process dunning sweep, demo dataset seeder), gated behind a `simulation-operator` JWT claim issued per-org. `RenewalCronService` renews due subscriptions inside the same atomic cross-module transaction as M4's Billing/Payments coordinator, now joined by Webhooks — one invoice per renewal even under concurrent workers, proven by an HTTP-level concurrency test.
- **Frontend:** Developers page extended with a Webhooks section (endpoint registration with a one-time secret reveal, org-wide "Dispatch pending deliveries"), an expandable JSON event timeline with per-delivery-attempt detail, and the Simulation Bar fully wired to the real API (live virtual clock, all five time-travel/ops actions, error/retry state on clock-load failure).
- **Scope discipline:** the pre-M5 speculative frontend contract (secret reveal/regenerate, endpoint activate/deactivate, per-event resend) was intentionally *not* built — the real backend never grew those endpoints, and the team chose to match the real backend exactly rather than ship dead UI for non-existent features (per this project's standing "no fake screens" rule).
- **Hardening from QA (Codex QA independent adversarial pass + Antigravity security review, both real, both found genuine issues — no BLOCKER, 9 IMPORTANT, fixed same session):**
  - **Dispatch lease had no stale-owner fencing:** a worker that stalled past its 5-minute lease could still persist its own delivery outcome after another worker reclaimed and delivered the same event. Fixed — the final `MarkDispatched`/`ScheduleRetry`/delivery-attempt persistence is now a single UPDATE guarded by `dispatch_lease_id = <this worker's lease>`; a lost race is silently discarded, matching the project's "duplicate webhook delivery → effect once" invariant for real this time (the M5 test suite's original happy-path test didn't catch this — added `Dispatcher_discards_outcome_when_its_lease_is_reclaimed` to prove it).
  - **SSRF via DNS rebinding:** the destination URL was DNS-validated, then `HttpClient` independently re-resolved the hostname to actually connect — a small window for a public hostname to flip to a private/loopback address between the two. Fixed with a `SocketsHttpHandler.ConnectCallback` that connects directly to the already-validated IP (redirects and proxying disabled), closing the TOCTOU gap entirely rather than re-validating and hoping.
  - **`subscription.changed`'s payment failures were missing `dunning.outcome`:** the normal per-invoice payment path emits it on Declined/InsufficientFunds; the subscription-change-triggered payment path didn't. Webhook consumers now get the same failure signal from both paths.
  - **Webhook endpoint registration advertised idempotency it didn't implement:** the frontend sent an `Idempotency-Key` (matching this project's established convention) but the handler always created a new endpoint. Implemented the same DB-unique-constraint replay/409 pattern used everywhere else in this codebase (Subscriptions, Payments) rather than a one-off mechanism.
  - **Zero M5 tenant-isolation tests existed**, despite tenant isolation being a non-negotiable, BLOCKER-class domain invariant for every other module. Added coverage proving org A cannot read or mutate org B's webhook endpoints/events/deliveries or trigger org B's simulation actions — uniform 404, no existence oracle.
  - Frontend a11y: fixed a duplicate-`id`/broken-label association on the webhook secret field, added a visible/announced error+retry state when the Simulation Bar's clock query fails (it previously failed silently forever), synced the frontend's minimum secret length to the backend's real 32-character minimum, added a clipboard-failure path and live-region announcements matching the M4 async-state precedent.
  - **Test-suite honesty finding (Codex QA):** the original 6 M5 integration tests exercised the happy path of each scenario but didn't prove the concurrency/tampering edge cases the roadmap actually cares about (e.g. the duplicate-delivery test never ran two workers concurrently). The suite grew from 6 to 11 tests specifically to close that gap — lease-reclaim, endpoint idempotency conflict, malformed input, tenant isolation, and the dunning-outcome regression are now each independently proven, not just implied by the happy path.
- **Deferred, consciously (not this milestone):**
  - **`IVirtualClock` is a process-global singleton, not per-organization** — one org's time-travel action moves every org's renewal eligibility, retry timing, and HMAC replay window. Real finding, real architectural cost to fix properly (every clock consumer — `RenewalCronService`, the webhook dispatcher, dunning sweep — would need an org-scoped clock context). This is a single-operator portfolio demo, not concurrent multi-tenant production traffic, so the risk is accepted for now; revisit if M6 ever needs true concurrent-tenant simulation.
  - `SimulationSeeder` isn't concurrency-safe (two simultaneous "Seed Demo Dataset" clicks can create duplicate catalog rows) — low-stakes internal demo tooling, not a financial-correctness path, accepted as-is.
  - Webhook secret rotation (dual-secret grace period) and encryption-at-rest for stored secrets — real security hardening, correctly scoped to M6's "full security review pass," not a webhook-feature gap.
- **This was the milestone with the highest-value test scenarios**, and it earned the hard review — see Test Strategy below.

### M6 — Analytics & Production Polish (stretch) — CORE DONE, CLOSING TASKS REMAIN
- **Backend: Reporting module — DONE, CI-green.** Tenant-scoped append-only source-event log (idempotent on source-event-id) fed by immutable before/after facts from Subscriptions (create/change/renew/status transitions) and Catalog (price updates), each written inside the same shared cross-module transaction as the domain mutation (`FinancialTransactionCoordinator` / new `PriceMutationCoordinator`). Rebuildable `subscription_snapshots` + an `mrr_movements` waterfall ledger derive integer-cent annualized run-rate per pricing model, with New/Expansion/Contraction/Churn attribution, per-currency current MRR/ARR/PastDue-at-risk totals, and a `/api/reporting/summary|waterfall|events/{id}|rebuild` HTTP surface (tenant-scoped, uniform 404s). Catalog `Price` gained a `Version` column so a subscription's revenue fact stays pinned to the price terms it actually saw. See `backend/src/Modules/Reporting/REPORTING_DESIGN.md`.
  - **Hardening from QA (Codex QA independent adversarial pass):** a BLOCKER — a movement's "before" amount was read from the live replay snapshot instead of the fact's own immutable Before terms, so out-of-order ingestion with a version gap silently mis-attributed delta and left the waterfall unreconciled against the final snapshot. Fixed to always derive from `fact.Before`; regression test reproduces the exact gap (ingest order v1/v3/v2), confirmed passing against real PostgreSQL.
  - **Second independent adversarial pass (Codex QA, part of the M6 security review):** no BLOCKER. Confirmed cross-tenant access to `summary|waterfall|events/{id}|rebuild` uniformly 404s (never a 403 oracle), `rebuild` cannot target another org, and duplicate source-event delivery is a genuine no-op under concurrency (`(organization_id, source_event_id)` unique constraint + `ON CONFLICT DO NOTHING`). Strengthened the out-of-order regression test with direct Before/After assertions and added a true 8-way concurrent-duplicate-delivery test and cross-tenant rebuild/waterfall non-interference checks.
  - **Third hardening finding (codex-security scan artifact, excluded from the security report as not a tenant-boundary issue but flagged as a validated financial-correctness defect; fixed by Claude — Backend Fallback on a Codex — Backend usage-limit handoff):** a transition's own immutable Before terms could themselves be stale — a subscription transition computed before an intervening Catalog price mutation, but whose reporting fact was ingested after that mutation had already revalued the live snapshot, still referenced the pre-mutation price. Diffing that stale Before against the correctly-revalued After double-counted the price mutation's own delta as a second movement in `mrr_movements`/the waterfall (current ARR/at-risk ARR were already correct — only the ledger double-counted). Fixed in `ReportingService.ApplySubscription` by applying the same already-superseded-price supersession check already used for After to Before as well, so a stale Before is revalued against the latest applied price terms before diffing — this does not touch the separate out-of-order/version-gap code path from the first BLOCKER fix above. Regression test reproduces the exact ingest order (create on v1 → price mutation v1→v2 → PastDue transition still carrying v1 Before/After terms), asserting ARR/at-risk ARR, the exact movement rows, and the waterfall, against both the live streaming path and `RebuildAsync`.
  - **IMPORTANT, deferred:** `POST /api/reporting/rebuild` replays a tenant's full source-event history synchronously, and `waterfall` loads all prior movements for the requested range into memory unbounded (`ReportingService.cs` ~91-139, ~342-379) — a same-tenant resource-exhaustion risk (requires an already-authenticated `simulation-operator` token for that org, not a cross-tenant exploit), not urgent enough to redesign mid-milestone. Real fix is architectural (async/queued rebuild, SQL-aggregated/paginated waterfall, tenant quotas) — revisit if this ever needs to hold more than a demo-scale tenant history.
  - **Deferred, consciously:** backfilling Reporting facts for subscriptions that predate this module — today's mutable Catalog prices can't safely stand in for the price terms an old transition actually saw. Also: the `simulation-operator` JWT claim is tenant-wide (minted whenever `SimulationModeEnabled`), not role-scoped — any member of a simulation-enabled org can trigger `rebuild`, and a token stays valid until expiry even if the flag is later disabled. Accepted for a single-operator demo; would need a real role check if this became multi-operator.
- **Frontend: Executive dashboard — DONE, CI-green.** Hero KPI grid (MRR/ARR/Active Subscriptions/Net MRR Growth 30d), At-Risk Revenue Alert banner (mirrors the M4 dunning callout, only renders when at-risk ARR > 0), MRR Waterfall card (proportional Tailwind bars, no chart dependency), all built on the real `/api/reporting/*` contract. ## Test strategy — required scenarios

These map directly to the domain invariants in `docs/ARCHITECTURE.md` and must exist as real integration tests, not just asserted in code review:

1. **Duplicate webhook delivery → effect occurs once** (Inbox unique-constraint test).
2. **Two concurrent renewal-cron workers → no duplicate invoice** (optimistic concurrency / row-lock test).
3. **Duplicate payment request (same idempotency key) → no duplicate charge/effect.**
4. **Cross-tenant access attempt → denied** (IDOR test per module with data).
5. **Failed payment → dunning retry policy fires on the correct virtual-clock schedule.**
6. **Out-of-order event ingestion → safe, no corrupted state.**

## Deployment strategy

Docker Compose for local dev (Postgres + api + web, matching Fleet/CMMS/HelpDesk/Order&Inventory conventions). Render.com (`render.yaml`) as the deploy target once M1–M5 are stable — same platform as the rest of the portfolio, keeps deployment familiar and low-effort so the project can focus on domain/backend depth.
